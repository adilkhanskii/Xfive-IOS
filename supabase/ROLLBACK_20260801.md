# 2026-08-01 backend release and rollback runbook

Status: review/staging only. None of the five new migrations may be applied to
production until the compatible clients, backups, secrets, and staging evidence
below exist.

## 1. Backup before any release write

Keep the database URL and generated files outside the repository. The commands
below are examples for an operator shell; never paste the password or dump into
an issue, log, mobile build, or chat.

```sh
export X5_DATABASE_URL='postgresql://...'
export X5_BACKUP_DIR='/absolute/operator-controlled/x5-20260801'
mkdir -p "$X5_BACKUP_DIR"

pg_dump --dbname="$X5_DATABASE_URL" --format=custom --no-owner --no-privileges \
  --file="$X5_BACKUP_DIR/full-before-release.dump"
pg_dump --dbname="$X5_DATABASE_URL" --schema-only --no-owner --no-privileges \
  --file="$X5_BACKUP_DIR/schema-before-release.sql"
pg_dump --dbname="$X5_DATABASE_URL" --data-only --no-owner --no-privileges \
  --schema=public --schema=storage \
  --file="$X5_BACKUP_DIR/public-storage-data-before-release.sql"
sha256sum "$X5_BACKUP_DIR"/*
```

If only the Supabase CLI is available, create a second logical dump and verify
that it is non-empty before proceeding:

```sh
supabase db dump --project-ref afwznqjpshybmqhlewmy \
  --file "$X5_BACKUP_DIR/supabase-schema-before-release.sql"
supabase db dump --project-ref afwznqjpshybmqhlewmy --data-only \
  --file "$X5_BACKUP_DIR/supabase-data-before-release.sql"
```

Record counts for `messages`, `notifications`, `tasks`, `task_responses`,
`portfolio_items`, `push_tokens`, and `storage.objects` before and after. A SQL
dump contains Storage metadata, not the object bytes. The release does not
delete or rewrite chat objects, but an independent provider-level Storage
backup is still required by the production backup policy.

## 2. Mandatory staged release order

1. Review the four migrations and this rollback with a second operator.
2. Provision APNs, FCM HTTP v1, `WEB_APP_URL`, and the dedicated webhook secret.
   Put the same webhook secret in Vault as `x5_push_webhook_secret`; do not print
   it.
3. Deploy `send-message-push`, verify signed health, then exercise one APNs,
   Android FCM, and web FCM staging token. A success plus a transient second
   target must remain retryable; an explicitly invalid owned token must be
   removed without logging it.
4. Apply `20260801115000_push_tokens_contract.sql`. Confirm the preflight sees
   no duplicate user/platform pairs and resolves duplicate provider-token
   ownership deterministically, then deploy `register-push-token`. Stage-test
   atomic account reassignment plus exact `(user_id, platform, token)` deletion;
   a stale logout must not delete or clear a newer account's token.
5. Apply `20260801120000_secure_push_dispatch.sql`. Verify the outbox cron,
   message notifications, task-response notification, and atomic
   `x5_accept_task_response` call. Accepting one response must mark every other
   response to that task `rejected` in the same transaction.
6. Deploy clients that understand private signed chat-media URLs, upload only
   `<chat_id>/<user_id>/<filename>`, and accept both that layout and read-only
   legacy `chats/<chat_id>/...` rows. Verify image, `audio/webm`, and video on
   iOS/web/Android.
7. Generate a separate random value of at least 32 characters. Store it as Edge
   secret `X5_PORTFOLIO_MODERATION_SWEEP_SECRET` and, with the identical value,
   as the single Vault entry `x5_portfolio_moderation_sweep_secret`. Never log
   or paste it into SQL/source. Deploy `moderate-portfolio`, then apply
   `20260801121000_portfolio_automatic_moderation_enforcement.sql`.
   Verify safe=`approved`, unsafe=`rejected`, provider failure=`pending`, and no
   manual/developer approval path. Verify the minute cron claims with hashed
   leases and stops after five provider/preparation failures.
8. Apply `20260801122000_secure_chat_attachments.sql`. Confirm the bucket
   is private, legacy reads still sign, cross-chat references fail, new legacy
   canonical uploads work, the temporary owner/member legacy upload route
   expires at `2026-09-01 00:00 UTC`, and 12 MiB image / 20 MiB audio / 47,000,000-byte video
   limits hold. The video path must use the rotating-JWT TUS uploader; the
   ceiling stays below the Supabase Free 50 MB project limit.
9. Apply `20260801123000_private_portfolio_media.sql` only after compatible
   signed-URL clients are active. The migration retains legacy public-form URL
   strings as identifiers but makes their bytes private. Verify owner/approved
   signing and rejected/orphan cleanup.
10. Observe outbox `pending`, `in_flight`, and `dead` counts plus Edge error rate
   for one full retry window before expanding the rollout.

## 3. Safe operational rollback

Do not immediately roll back a private chat bucket while new clients are still
writing data. Stop rollout first and choose a compatible client version.

1. Stop traffic expansion. Export these rows for incident evidence:

   ```sql
   select status, count(*) from public.push_webhook_outbox group by status;
   select status, count(*) from public.push_dispatches group by status;
   ```

2. Let `pending`/`in_flight` outbox rows reach `delivered`/`dead`, or export and
   account for every unfinished event. The rollback SQL refuses to run while an
   unfinished event exists.
3. Run `rollback/20260801_safe_operational_rollback.sql` in a reviewed database
   session. It pauses provider push and the moderation sweep, restores the
   public chat transport needed by old clients, and restores the prior compact
   automatic-only portfolio row RLS. It deliberately does not make portfolio
   media public.
4. Verify all pre-release user-table row counts are unchanged and sample old
   and new chat objects. The script contains no `DELETE`, `TRUNCATE`, object
   removal, or user-table drop.
5. Roll back the Edge Function/client artifacts to the reviewed versions.
   Never restore the old anonymous push body containing caller-selected actor,
   recipient, or text.

The operational rollback intentionally retains the outbox, dispatch and task
event ledgers, the atomic task-acceptance RPC, canonical task-response identity,
and the stricter message insert policy. Those are security/data-integrity
controls, not disposable user data. Remove them only through a separate later
migration after backup comparison, client retirement, and the 30-day retention
window. Re-applying the release migration and rescheduling its jobs resumes the
signed dispatcher.

The rollback also retains both canonical `push_tokens` unique keys and the
owner-only read policy. Token mutation remains behind the authenticated Edge
route and service-role register/unregister RPCs so account switching cannot
leave one provider token attached to multiple users. Loosening anonymous or
authenticated table-write grants is not a safe rollback step.

The moderation queue and its hashed leases are retained. While its cron is
paused, pending items remain private. Resume only after the Edge/Vault sweep
secrets match. Secret rotation follows the pause-update-verify-reschedule order
in `BACKEND_RELEASE_READINESS.md`; rollback never requires revealing a value.

## 4. Restore drill

Before production, restore `full-before-release.dump` into an isolated database
and compare schema plus the recorded counts. A backup that has not passed a
restore drill is not an accepted release gate.
